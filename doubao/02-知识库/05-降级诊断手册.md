# 降级诊断手册（没有脚本时怎么查）

> 用途：豆包/扣子不能运行 Python 脚本。当用户不方便跑 `mc_audit.py` 时，
> 用这份手册一步步手工定位。每条都给「让用户执行的命令 → 判读方法 → 处置」。

---

## 通用准备：先要三样东西

不管什么症状，先让用户提供：

1. **环境**：MC 版本 / 加载器与版本 / 模组数量
2. **日志**：`logs/latest.log`，或启动器控制台输出的最后 30 行
3. **改动**：最近装了什么、卸了什么、换过什么材质包

没有这三样，任何结论都是猜。

## 场景 1：启动崩溃（进不到主菜单）

### 让用户执行
```bash
# 启动器控制台一般直接可见；若已退出，看崩溃报告
ls -t <实例目录>/crash-reports/*.txt | head -1
```

### 判读
在崩溃报告或控制台里找这三类关键词：

| 关键词 | 含义 | 下一步 |
|---|---|---|
| `HARD_DEP_NO_CANDIDATE` / `Incompatible mods found` | 依赖版本区间不满足 | 看它说的「已安装版本」与「需要版本」 |
| `NoClassDefFoundError` / `ClassNotFoundException` | 某个类不存在，通常是模组版本错配 | 看 `Caused by` 指向哪个包名，升那个模组 |
| `Mixin apply failed` / `Mixin target ... was not found` | 注入目标不存在 | 多为可选兼容失效，未必致命 |

### 处置
- 依赖不满足：**按它给的版本号装，不要按 MC 版本号猜**。
- 缺类：把 `Caused by` 里的包名对应到模组，升到含该类的版本。

**反例（真实踩过）**：`reeses-sodium-options 1.8.3+mc1.21.4` 在 1.21.1 上工作正常，
因为它的 `depends.sodium` 是 `>=0.6.5`。有人看到 `+mc1.21.4` 以为版本不对，升到 `2.2.4`，
结果它硬依赖 `sodium =0.8.13`，直接崩。**版本号里的 MC 号是构建标记，不是兼容声明。**

## 场景 2：第一人称动作没了

### 让用户执行
```bash
grep -o 'resourcePacks:.*' <实例目录>/options.txt
```

### 判读
- 如果列表里有 `punchy:punchy` → 动画包已启用，问题在别处
- 如果**没有** `punchy:punchy`，但 `mods` 里有 `punchy` → **这就是原因**
- 如果 `mods` 里既没有 EMF/ETF 也没有 FreshAnimations 包 → 是根本没有动画体系

### 为什么
Punchy 是「模组本体 + 内置资源包」两件套。本体负责注入渲染逻辑，动画数据全在 `punchy:punchy` 里。
只装本体不带包，游戏内会弹 `PUNCHY: RESOURCE PACK DISABLED`，动作全部失效。

### 处置
选项 → 资源包 → 勾选 Punchy!（或直接把 `punchy:punchy` 加到列表末尾）。

## 场景 3：手持火把不照亮

### 让用户执行
```bash
ls <实例目录>/mods | grep -iE 'lambdynlights|lucent|dynamic.?light'
```

### 判读
- 有输出 → 已装动态光源，问题在配置或光影覆盖
- **无输出** → 全包没有动态光源模组

### 为什么
这是个常见的**功能误解**：玩家以为「原版应该有」，其实原版手持火把不照亮周围，
需要专门模组。所以这是「功能不存在」，不是「参数配错」。查配置只会白费时间。

### 处置
装一个动态光源模组（LambDynamicLights 最常见）。**只装一个**，装两个会光照叠加过曝。

## 场景 4：画面整体发糊

### 让用户执行
```bash
grep -i 'limits mip level' <实例目录>/logs/latest.log | head -20
```

### 判读
输出形如：
```
Texture yuushya:0extra_building_material/preview/... with size 24x32 limits mip level from 4 to 3
```
**有输出** = 存在非 2 次幂贴图，正在拖累该贴图的 mipmap 链。
**注意**：单张贴图只影响它自己；只有当**方块/物品图集里**的贴图不是 2 的幂时，才会让整片区域发糊。

### 判据（自己算）
- 宽必须是 2 的幂（16/32/64…）
- 高是 2 的幂，**或**是宽的整数倍（如 16×48 是合法动画条）
- 带 `.png.mcmeta` 的不要改——帧尺寸写死在元数据里

### 处置
优先怀疑家具类模组（它们爱用 24×24 / 48×48）。做覆盖包把这些贴图补成 2 的幂，
放到资源包列表**最后一项**（最高优先级）。

## 场景 5：方块透明 / 紫黑

### 让用户执行
```bash
grep -iE "Failed to load model|missing model for variant|Unable to load model" <实例目录>/logs/latest.log | head -20
```

### 判读
- `missing model for variant: 'xxx#facing=north'` → blockstate 里少写了一个变体
- `Failed to load model xxxyyy.json` → 模型文件本身有问题或不存在
- 出现 `JsonSyntaxException: Missing texture` → 模型 `faces` 里缺 `texture` 字段

### 处置
先判断责任方：
- 缺失的文件在**模组 jar 里就没有** → 上游问题，客户端补不了，只能避开该方块
- 文件在，但被材质包覆盖坏了 → 移除或替换那个材质包
- 只是 blockstate 属性代差（如 1.21.4 的 `axis` 跑到 1.21.1 上）→ 补一个对应版本的 blockstate

## 场景 6：卡 / 掉帧

### 让用户执行
进游戏按 **F3**，读三行：

```
XX fps
C: ... 
E: ...   （或 GPU: XX%）
```

### 判读（关键：三个数缺一不可）
| 现象 | 含义 | 方向 |
|---|---|---|
| GPU 接近 100%，帧率低 | 显卡瓶颈 | 降渲染距离 / 关光影 / 降分辨率 |
| GPU 不高，但 `ms tick` 接近 50 | CPU/逻辑瓶颈 | 找实体过多的区域、检查模组 tick 逻辑 |
| GPU 不高，tick 也正常，帧率仍低 | 帧生成/模组渲染层问题 | 查渲染类模组叠加 |

**不要**在没看这三个数之前就建议「降低画质」——如果瓶颈在 tick，降画质完全无效。

### 处置
按瓶颈类型处理。同时提醒：**不要叠加第二套优化模组**，两个改同一系统的模组会互相打架。

## 场景 7：砍树时灵时不灵

### 让用户执行
打开 `<实例目录>/config/treechop-client.toml` 与 `treechop-common.toml`，看四个键。

### 判读
| 键 | 若为此值则有问题 |
|---|---|
| `choppingEnabled` | `false` → 完全不砍 |
| `sneakBehavior` | `"INVERT_CHOPPING"` → 潜行会**关闭**砍树 |
| `treesMustHaveLeaves` | `true` 且是模组树 → 树叶不在原版标签里，判定为无叶，不倒 |
| `choppingRequiresCorrectToolForDrops` | `true` 且模组原木声明工具需求 → 空手不触发 |

### 先确认真的没生效
TreeChop 会在准星旁显示 `Chopped <方块> n/m 次`。
**HUD 有计数 = 功能正常**，问题在别处，此时不要再改配置。

## 通用处置原则（每次都适用）

1. **一次只改一个变量**，改完立刻测。
2. **改前备份**，备份不能放在 `mods/` 或 `resourcepacks/` 里（会被扫描）。
3. **优先级**：改配置 &gt; 装/换模组 &gt; 打局部补丁 &gt; 换整套资源。
4. **区分责任**：上游问题不要包装成「已修复」，直接说明「作者没发这个资源，客户端补不了」。
