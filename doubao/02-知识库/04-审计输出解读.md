# 审计输出解读指南

> 用途：用户把 `mc_audit.py` 的输出贴给你时，你要能读懂它。
> 这份文档也是用户自己看报告的对照表。

---

## 一、控制台输出长什么样

```
实例 <实例目录>
模组 158 / jar 158 / 材质包 16
严重 1 · 隐患 2 · 记录 4

[CRITICAL] 51 个模型被引用但不存在
           skniro_furniture:block/bamboo_sign ← [Skniro的家具] SkniroFurniture-1.5.0.jar:assets/skniro_furniture/blockstates/bamboo_sign.json
[WARN    ] 31 个模型 parent 缺失
           mcwfurnitures:block/parent/desk；mcwfurnitures:block/parent/drawer_base
[INFO    ] 7 张非 2 次幂贴图带 .mcmeta，保留原尺寸
```

`←` 左边是**缺失的东西**，右边是**谁在引用它**（`jar 名:内部路径`）。

## 二、三个等级的含义（不要混用）

| 等级 | 含义 | 用户该做什么 |
|---|---|---|
| `CRITICAL` | 会导致功能失效或启动失败 | 必须处理，或明确接受 |
| `WARN` | 有隐患，可能没有立即表现 | 知道它，观察是否引发问题 |
| `INFO` | 记录性信息，多数是「已知且无害」 | 了解即可，不要当成故障 |

**最常见的误读**：把 `INFO` 当成「没问题」。`INFO` 里有些条目正是解释「为什么某个现象看起来奇怪但不用改」，
例如「8 张非 2 次幂贴图带 .mcmeta，保留原尺寸」——这是**故意不改**，因为改了会破坏动画帧布局。

## 三、六类结论怎么判读

### 1. 模型被引用但不存在
```
skniro_furniture:block/bamboo_sign ← [Skniro的家具] ...jar:assets/...blockstates/bamboo_sign.json
```
**含义**：blockstate 指向的模型文件在包里根本没有。
**后果**：该方块渲染成透明或紫黑。
**处置**：这几乎总是**模组作者漏发资源**。先确认已是最新版；是则属上游问题，客户端补不了，只能避开这些方块。

### 2. 模型 parent 缺失
```
mcwfurnitures:block/parent/desk
```
**含义**：模型继承的父模型不存在。同上，多为模组自身问题。
**注意**：如果缺失的是 `minecraft:block/xxx` 这类原版模型，说明**审计没读到原版客户端 jar**，
那是工具环境问题（版本隔离时实例目录里没有 `minecraft.jar`），不是游戏问题。要提醒用户用 `--vanilla` 指定。

### 3. 模型字段写坏
```
yuushya/.../easel_hitbox.json（78 个 face 缺 texture）
```
**含义**：模型 JSON 里 `faces` 写成空对象 `{}`，缺 `texture` 字段，加载时抛 `JsonSyntaxException`。
**后果**：多数是**没有任何 blockstate 引用的死文件**，不影响画面，只刷日志。
**处置**：可以用覆盖包补一个合法空模型来消错；也可以不管。

### 4. 贴图 mipmap 三分类
| 分项 | 含义 | 处置 |
|---|---|---|
| `blocking` | 会压塌图集 mipmap 且没被覆盖 | 必须修：补成 2 的幂 |
| `deferred` | 非 2 次幂但带 `.mcmeta` | **不要修**：帧尺寸写死，改了破坏动画 |
| `covered` | 已被修复覆盖包处理 | 已完成，确认覆盖包在最顶层即可 |

**判据**：只有 `textures/block` 与 `textures/item` 进图集。宽必须是 2 的幂；高是 2 的幂，或是宽的整数倍（动画条）。

### 5. 动画栈 facts
```
entity_model_features: 3.3.12
entity_texture_features: 7.2.7
fresh_animations_packs: [file/FreshAnimations_v1.11.2.zip]
punchy: {enableMod: true, animationSpeed: 5.5}
```
**判读要点**：
- EMF 与 ETF 都在 ≠ 有动画。还得 `fresh_animations_packs` 非空。
- `punchy.enableMod` 为 true ≠ 第一人称动作正常。还要 `resourcePacks` 里有 `punchy:punchy`。
- 这两个是**两件套陷阱**，是本工具最有价值的检查项。

### 6. 日志归因
```
[WARN] 4 处 mixin 目标缺失
       exposure→fuzs.easyanvils.world.inventory.ModAnvilMenu
```
**含义**：某模组想注入的类不存在，通常是**可选兼容**失效，不影响主体功能。
**判读**：只有当用户报告的功能**正好属于那个模组**时，才需要处理。

## 四、JSON 报告结构（用户贴 JSON 时看这里）

```json
{
  "summary": { "mods": 158, "jars": 158, "packs": 16,
               "critical": 1, "warn": 2, "info": 4 },
  "findings": [ { "severity": "...", "title": "...", "detail": "..." } ],
  "details": {
    "mipmap":   { "blocking": [], "deferred": [], "covered": [] },
    "animation":{ "facts": {}, "problems": [] },
    "treechop": { "installed": true, "facts": {}, "problems": [] },
    "assets":   { "missing_models": {}, "missing_parents": {}, "malformed": {} },
    "log":      { "mixin_misses": [], "top_errors": [] },
    "pack_entries": [ { "index": 0, "entry": "...", "format": 34 } ],
    "options":  { "renderDistance": "6", "simulationDistance": "5" }
  }
}
```

**读法**：先看 `summary.critical` 是不是 0；不为 0 就看 `findings` 里 `severity=critical` 的条目；
`details` 是给具体排查用的原始数据，不要一次性全读给用户。

## 五、让用户贴什么、不贴什么

**要贴**：`summary` 三行 + 所有 `critical`/`warn` 的 `title` 与 `detail`。
**不要贴**：完整的 `details`（几百行，且大部分与当前问题无关）。

如果用户贴了完整 JSON，你只提取与当前症状相关的那一段，其余不要复述。

## 六、报告里不会出现的东西（别问它要）

- 不会告诉你「哪个模组最耗性能」——那需要 profiler
- 不会判断存档是否损坏——不在范围内
- 不会检查服务端——只做客户端静态审计
- 不会给模组打分或推荐替代品——那是选型，不是诊断
